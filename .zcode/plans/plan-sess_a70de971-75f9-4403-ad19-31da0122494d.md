# 文件拖入终端 → 填充路径(基于 WebView2 新 API 的轻量方案)

## Context(问题与根因)

从资源管理器拖文件到终端没有任何反应。根因:窗口 `dragDropEnabled: false`(SFTP 的 HTML5 拖放上传依赖它),而终端区域没有任何 drop 处理;且 HTML5 drop 的 `File` 对象在 JS 里拿不到完整路径(`File.path` 是 Electron 专有)。

**更正之前的信息**:经查 [WebView2Feedback#501](https://github.com/MicrosoftEdge/WebView2Feedback/issues/501) 官方已于 **2023-04-24 关闭为已完成**——SDK **1.0.1777** 起该能力以稳定 API 落地,形态是宿主侧通道:页面调 `window.chrome.webview.postMessageWithAdditionalObjects(msg, files)` 把 drop 拿到的 File 传给宿主,宿主在 `WebMessageReceived` 的 `AdditionalObjects` 里拿 `ICoreWebView2File` 的 **`Path`** 属性(官方确认对 DataTransfer 的 FileList 有效)。JS 侧依然拿不到路径,所以必须经 Rust 宿主中转一次。

**本方案的关键优势**:`dragDropEnabled` **保持 false 不动**,SFTP 面板、LocalFilesDrawer 的"从资源管理器拖入上传"完全不受影响、零迁移;纯浏览器调试模式也不受影响。已验证:
- 项目已在 `src-tauri/src/lib.rs:91` 用 `with_webview` + `webview2-com` 0.39 做过同样的 WebView2 互操作(版本注释:tauri 2.12 → wry 0.57 → webview2-com 0.39);
- wry 的 `add_WebMessageReceived`(webview2/mod.rs:971)是追加式注册,自加的处理器可共存;
- 所需接口在钉住的 webview2-com-sys 0.39.1 里齐全:`ICoreWebView2File::Path`、`ICoreWebView2WebMessageReceivedEventArgs2::AdditionalObjects`、`ICoreWebView2ObjectCollectionView`;
- 位置信息用 HTML5 drop 事件自带的 `clientX/clientY`(CSS 像素),**不需要**任何 dpr/坐标换算。

行为目标(对齐 Windows Terminal / Xshell):拖文件到终端 → 光标处**填充路径、不回车**;含空格等特殊字符的路径包双引号;多文件空格连接;本地与 SSH 会话一致(插本地路径原文)。

## 实现方案

数据流:`drop` 事件(带 clientX/Y)→ JS 调 `postMessageWithAdditionalObjects({kind,x,y}, files)` → Rust WebMessageReceived 处理器取 AdditionalObjects 的 Path → `webview.eval()` 派发回页面 → 元素定位派发 `ashell-drop` CustomEvent → TerminalView 粘贴。

### 1. 后端新增小模块 `src-tauri/src/file_drop_bridge.rs`(`#[cfg(windows)]`,非 Windows 空实现)
- 命令 `install_file_drop_bridge(webview: tauri::Webview)`:App 每个窗口启动时 invoke 一次;用项目已有的 `webview.with_webview(|platform| ...)` 拿 `ICoreWebView2Controller` → `CoreWebView2()` → `add_WebMessageReceived` 追加处理器。用 `OnceLock<Mutex<HashSet<label>>>` 防重复安装(重复会双发事件)。
- 处理器逻辑:
  - `args.cast::<ICoreWebView2WebMessageReceivedEventArgs2>()` → `AdditionalObjects()`,count 为 0 直接返回;
  - 逐项 `cast::<ICoreWebView2File>()` 收集 `Path()`(PWSTR 转字符串);非 File 对象跳过;
  - 读 `WebMessageAsJson()` 里的 `{kind:"ashell-file-drop", x, y}`(kind 不符则忽略,不干扰 wry 自身 ipc);
  - `webview.eval(&format!("window.__ashellFileDrop&&window.__ashellFileDrop({})", payload_json))` 派发回同一 webview(payload 含 x/y/paths,serde_json 序列化,路径安全内嵌)。
- `lib.rs` 注册命令。复用 lib.rs 现成的 windows/webview2-com 依赖(169-176 行,无需改 Cargo.toml)。

### 2. 前端桥 `src/composables/useFileDropBridge.ts`(新)
- `installFileDropBridge()`:`isTauri` 且 Windows 时 `invoke("install_file_drop_bridge")`;
- 定义全局派发器 `window.__ashellFileDrop = ({x, y, paths}) =>` `document.elementFromPoint(x, y)?.dispatchEvent(new CustomEvent("ashell-drop", { detail: { paths }, bubbles: true }))`;
- `App.vue` setup 里调用一次(主窗口与所有弹窗共用 App.vue,一处覆盖全部)。

### 3. 终端 `src/components/TerminalView.vue`(唯一改动的业务组件)
- `.terminal-host`(2017 行)加 `@dragover.prevent` + `@drop="onTermFileDrop"` + `@ashell-drop="onDroppedPaths"`;
- `onTermFileDrop(e)`:preventDefault;`e.dataTransfer.files` 为空返回;守卫 `window.chrome.webview?.postMessageWithAdditionalObjects` 不存在(旧 Runtime / 非 Windows)直接返回(维持现状);否则同步调用它,消息体 `{ kind: "ashell-file-drop", x: e.clientX, y: e.clientY }`,附加 `[...e.dataTransfer.files]`(必须同步取,同 SftpDrawer 已验证的 DataTransfer 失效坑);
- `onDroppedPaths(e)`:格式化路径(含空白或 `" ' \` $ ; & | ( ) < > * ? #` 之一 → 包双引号;多文件空格连接)→ 复用现有 `pasteToTerminal()`(571 行,自带转义剥离 + bracketed paste,发送走 onData→WS 与键盘一致)。
- 说明:`dataTransfer.files` 应包含拖入的目录本身(Chromium 会合成 File 条目),实现时实测确认;若目录拿不到则作为已知限制记录(文件是主场景)。

## 已知边界(记录给用户)
- Windows(WebView2 Runtime ≥ 110,2023 年起的 Evergreen 自动更新均满足)生效;macOS/Linux 终端拖入维持现状(它们今天也不支持,无回归)。将来若要覆盖 mac/Linux,再用 Tauri 原生 dragDropEnabled 路线,且本方案派发的 `ashell-drop` CustomEvent 接口可直接复用。
- 拖入文本(非文件)不做处理。
